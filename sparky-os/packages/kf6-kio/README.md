# kf6-kio: Plasma's launcher on the Graphics page's GPU

Rebuild the edition's published kf6-kio 6.30.0-1+stereo3d7+lc1 as 6.30.0-1+stereo3d8+lc1 with the patches in `patches/` that its series does not carry yet (`EDITION-ONLY-start-no-application-whose-GPU-cannot-be-applied.patch`, ORDER 346g), then `sparky-os/translations/kf6-kio-gpu-launch.po.patch`.
The two earlier patches, `EDITION-ONLY-run-applications-on-the-GPU-of-the-graphics-settings.patch` and `EDITION-ONLY-start-activatable-applications-on-their-GPU.patch` (+stereo3d6, ORDER 239), are already in the published series.

KIO decides where an application started from its desktop entry runs in one place, `KProcessRunner::fromApplication` (`src/gui/kprocessrunner.cpp`): an entry with `PrefersNonDefaultGPU=true` gets `KIO::discreteGpuEnvironment()` (`src/gui/gpudetection.cpp`, from switcheroo-control, else Solid's `hasDualGpu`), every other entry starts with the session's environment.
The patch adds the other entries: when the entry sets neither `PrefersNonDefaultGPU` nor the older `X-KDE-RunOnDiscreteGpu`, and the launch environment chooses no GPU (`DRI_PRIME`, `MESA_VK_DEVICE_SELECT`, `VK_LOADER_DRIVERS_SELECT`, `__NV_PRIME_RENDER_OFFLOAD`, the variables libmedia-gpu-route also leaves to the launch), KIO runs `sparky-stereo-gpu-env --app MENU-ID` (or the desktop file's absolute path when it is outside the menu) and starts the application with the `VARIABLE=value` lines it prints.
That is the Graphics page's resolver (`sparky-stereo-graphics`), the same command `sparky-stereo-gpu-run` and libmedia-gpu-route ask; KIO keeps no policy of its own.
Without the command the launch is as it was: the Graphics page is not installed, so nothing was chosen.
When the GPU the person chose cannot be used (exit status 4), the application is not started on another GPU (Daniel, 2026-11-01: "either it works or not and the user must know"; ORDER 346g): the launch fails through KIO's own launch-failure path, the error of `KProcessRunner` that `ApplicationLauncherJob` turns into its `errorText`, which the caller's job UI delegate shows (in Plasma's task manager a KNotificationJobUiDelegate, so a notification), with the program's name and the command's own words: what failed, why and what to do. The command keeps the problem, and its notification offers "Use NAME" for each GPU that can draw.
A command that fails (another exit status), crashes, cannot be started or does not answer within five seconds (longer than its own three-second wait for power-profiles-daemon, so it says its own reason) is said the same way, and the application is not started either.
Automatic is a rule, not the person's choice: when it cannot place the application now (exit status 5, a browser while the power profile it follows cannot be read), the application starts as the session would, as before, and the command has said and kept why. sparky-stereo-graphics before 0.2.4 gives exit status 4 there too, so `libkf6kiogui6` Breaks it.
A D-Bus activatable application whose GPU cannot be applied is neither activated nor started.
An application that D-Bus would activate (`DBusActivatable=true`, started without files) is started by KIO itself when a GPU environment applies (KDE's own key or the resolver's answer) and its entry has an `Exec` line, since the session bus would start it without those variables; with no GPU environment it is activated as before.
Gwenview's videos follow Gwenview's own kind: its Categories (`Graphics;Viewer;Photography`) make it another program, which stays on the GPU that draws the desktop, and the page's per-program choice moves it.
Typed commands (KRunner's shell commands, an executable opened from Dolphin, `kstart COMMAND`) start where the session puts them: they have no desktop entry, so no kind, and KDE does not apply its own key to them either.

The tests are in `autotests/applicationlauncherjobtest.cpp`, with a stand-in resolver: `shouldRunOnTheGpuOfTheGraphicsSettings` (eleven rows, Automatic's exit status 5 among them), `shouldNotStartWhereItsGpuCannotBeUsed` (six rows: the person's choice that cannot be used, a resolver that fails, misses its libraries, crashes, cannot be started or hangs) and `shouldStartAnActivatableApplicationOnItsGpu` (three rows); Debian's build does not run them (`BUILD_TESTING=OFF`).

## Build

`build.sh` runs as root in a freshly updated Debian testing container whose APT has the published edition repository at priority 1001.
It takes the predecessor source from the signed index (`SPARKY_PUBLISHED_TREE`), checks every file the `.dsc` names against it, adds the patches after the existing series with quilt, writes the changelog entry once, installs the build dependencies and builds as UID 1000 with the source's own Lean Code hooks.
It then runs `lean.release check-debs` and `check-link --previous-dir "$SPARKY_LC_PREVIOUS_DIR"` (the predecessor's binary packages) from `SPARKY_RELEASE_TOOLKIT` (this tree's `sparky-os`), and stages the archives with `SHA256SUMS` in `OUT`.
The source's own Lean Code hooks (toolkit 0.1.20 since +stereo3d7) run the same link and start gate in `dh_builddeb`, so the build needs `SPARKY_LC_ARCHIVE_CONFIG` (the signed public archive sources, lean/archive.md) and `SPARKY_LC_SCRATCH` (the gate's own state), the public archives on the network, and bubblewrap running as the build user: in a container, `--security-opt seccomp=unconfined --security-opt apparmor=unconfined --security-opt systempaths=unconfined` (bubblewrap mounts a fresh /proc). The toolkit 0.1.20 in the source reads only the uri, suite, components, keyring and check_valid_until of each archive source: give it the sources without the `architectures` field that NVIDIA's CUDA repository gained on 2026-11-01 (KIO links nothing from it).
Only amd64 is built, as for the predecessor; no i386 twin exists for kf6-kio.
