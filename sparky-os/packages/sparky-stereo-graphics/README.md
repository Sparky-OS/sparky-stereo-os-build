sparky-stereo-graphics
The Graphics page of System Settings, Hardware: every graphics processor of the computer, the one that draws the desktop, and where each kind of program draws.

Dependencies:
-------------
KDE Frameworks 6 (KConfig, KCMUtils, KI18n, KService, Kirigami), Qt 6 (Quick, DBus), kdialog
Also: power-profiles-daemon, or tlp-pd (TLP) or tuned-ppd (TuneD), which provide the same power profiles
Recommended: switcheroo-control, hwdata

Build:
-------------
OUT=/path/in/workspace/pending-pack ./build.sh (inside a Debian container with KF6 development packages; node-acorn and python3-yaml for Lean Code)

Install:
-------------
su
apt-get install ./sparky-stereo-graphics_0.2.4_amd64.deb

Uninstall:
-------------
su
apt-get purge sparky-stereo-graphics

What the page shows and changes
-------------
- Graphics processors: one card per GPU (name from the PCI database, integrated or discrete, driver, the screens attached with their names from the EDID, what is placed on it now). A third card appears when a third GPU is installed. A chip that only shows a picture (a server board's BMC) is listed and never offered; a GPU the account may not open is listed with a hint.
- Main desktop GPU: Automatic (the GPU with the laptop panel, else the one with most screens) or any GPU that can render. It is written to ~/.config/sparky-stereo-graphicsrc and becomes KWIN_DRM_DEVICES at the next login (/etc/xdg/plasma-workspace/env/sparky-stereo-graphics.sh); the page says so and says which GPU the running session uses. A KWIN_DRM_DEVICES set by hand in ~/.config/plasma-workspace/env wins, and the page warns.
- Where programs draw: players, games, browsers and other programs, each Automatic, Follow the power profile, Integrated, Discrete or one GPU. Automatic is split by kind (Daniel, 2026-10-24): players, games and any program started in 3D go to the GPU measured best on this machine whatever the power profile, on battery too (the drops on the GPU that drives the screens are "avoidable by default, with the user choice imperating over it"); without a measurement that is the discrete GPU. Browsers follow the power profile: power saver the integrated GPU, performance the discrete GPU, balanced the GPU that draws the desktop. Other programs (Dolphin, Kate, System Settings) stay on the GPU that draws the desktop in every profile. Follow the power profile keeps the profile in charge for any kind. The person's choice always wins. The kind comes from the entry's Categories (Desktop Menu Specification): Game, WebBrowser, then Player or Video for players; an audio program without Video (Elisa) is another program. A program sent from an NVIDIA desktop to a Mesa GPU also gets Mesa's EGL and GLX vendors (__EGL_VENDOR_LIBRARY_FILENAMES, __GLX_VENDOR_LIBRARY_NAME), since glvnd would try NVIDIA's first.
- The machine record: /etc/xdg/sparky-stereo-graphicsrc, groups [Measured] (BestGpu, Model, Measurement) and [Decoding] (CopyBack), beneath the person's own ~/.config/sparky-stereo-graphicsrc. libmedia-gpu-route reads [Decoding] CopyBack from the same two files. sparky-stereo-gpu-record writes it: at boot (sparky-stereo-gpu-record.service) from the record shipped for a known model in /usr/share/sparky-stereo-graphics/machines, matched by the firmware's make and model and exactly the machine's display controllers; or from a measurement or an administrator on the machine (--set-best, --copy-back), which the boot service never replaces. A shipped record for another model is removed at boot, so a disk moved to another computer does not carry it. Shipped: the Lenovo ideapad 310-15ABR (A10-9600P), where 3D film dropped 589.6 frames a minute on the integrated R5 that drives the screens and 65.3 on the R5 M430, and copying decoded pictures back dropped more than software decoding (ORDER 234).
- Video decoding: "Copy decoded video back", the [Decoding] CopyBack key of the person's file. Off unless the person or the machine's record turns it on; a player's own decoder choice always wins, and MEDIA_GPU_ROUTE_COPY_BACK set in the session wins and the page says so.
- Programs: one list of menu entries, each "same as its group", "the dedicated GPU" or "the main GPU". The dedicated GPU means what KDE's launcher does with the key: the first discrete GPU, or no change when the GPU the computer starts with (its boot VGA) is already discrete. It is KDE's own PrefersNonDefaultGPU key in the person's copy of the entry (the same setting as Run Using Dedicated Graphics, written the way KMenuEdit writes it); there is no second list. A copy the page made follows the system entry when a package updates it, until the person edits it; an unchanged copy is deleted when the setting goes back to "same as its group".
- Paint windows (ORDER 518): how programs made with Qt Widgets (Konsole, Dolphin, Kate and the rest) paint their windows, for each kind of program and for each program: Automatic, On the processor, On the graphics card (batched), On the graphics card, Qt's OpenGL engine. All three ways stay the person's choice (Daniel, 2026-11-12: "keep as a option"; "the reason is offload the cpu load"). Automatic is each program's own (ORDER 554; Daniel, 2026-11-13: "I want the automatic per program for sure"): a program measured on this hardware to take less processor batched is painted batched, and a program not measured here, or measured no better, is painted by the processor ("leave it to iso 2": nothing is measured on the person's machine and nothing is guessed). The page says which, for each program: "Measured on this hardware: batched painting takes less processor.", "Measured on this hardware: batched painting takes no less processor." or "Not measured here: painted by the processor.". The measured record is one row for each program and card, [MeasuredPaintPrograms][ID.desktop][VENDOR:DEVICE] with Way (cpu or batch), Load.WORK (processor milliseconds for each frame asked, the program and the compositor together: the processor, batched, Qt's OpenGL engine), Runs.WORK (the quiet runs behind each number) and Source. It ships in share/machines for the hardware that was measured and reaches /etc/xdg/sparky-stereo-graphicsrc at boot (`sparky-stereo-gpu-record --apply-known`); `sparky-stereo-gpu-record --set-paint ID.desktop VENDOR:DEVICE cpu|batch|unset` writes a row measured on this machine, which takes the shipped record's place. The rule a row follows (ours; no recorded design): Way is batch only when every fixed work of that program on that card took at least a fifth less processor batched than on the processor, in quiet runs; a row that says batch against its own numbers is not followed. A machine is named by its firmware's vendor and product where they name a model, else by its processor's model name, and always by the exact set of its display controllers ([Match] Vendor, Product, Cpu, Gpus); a row is for the card the program is drawn on. The choices are in ~/.config/sparky-stereo-graphicsrc: [Paint] Players, Games, Browsers, Other and [PaintPrograms] ID.desktop, each cpu, batch or opengl; nothing is written for Automatic. The section shows with one GPU too.
  How it reaches a program: `sparky-stereo-gpu-env` adds `QT_WIDGETS_GPU_PAINT=batch` (or `=opengl`) to the lines it prints for a program, after the GPU's own variables, and Plasma's launcher (KIO) starts the program with them; `sparky-stereo-gpu-run` does the same for a program started by hand or from Steam, also when its caller chose the GPU. The edition's qt6-base reads the variable. Nothing is added for the processor. A `QT_WIDGETS_GPU_PAINT` the person set by hand in the session wins, and the page says so. A way the page chose for a program is that program's alone: the edition's Qt takes the variables out of its environment when it reads them, so a program started from a terminal or a file manager that paints on the graphics card does not inherit the way (a value set by hand, which comes without `QT_WIDGETS_GPU_PAINT_TELL`, is inherited as any variable is). Not reached: a program whose desktop entry sets PrefersNonDefaultGPU itself (KIO does not ask the page for those; its kind's and its own paint choice then need `sparky-stereo-gpu-run`), a typed command, an autostarted program.
  When it cannot be had: before the start, `sparky-stereo-gpu-env` says and keeps (problems engine, key `paint-NAME`) a way on the graphics card on a computer with no graphics processor that can draw, or with a Qt that has no such painting, and the program starts and paints on the processor. After the start only the program knows: `QT_WIDGETS_GPU_PAINT_TELL` names this command, and the edition's Qt runs `sparky-stereo-gpu-env --paint-failed PROGRAM CODE WORDS` when the session has no OpenGL, its OpenGL is drawn by the processor, Qt's OpenGL library cannot be loaded or the drawing surface cannot be made (key `paint-run-NAME`); it is kept until that program tells that the painting started (`--paint-ok`, asked for with `QT_WIDGETS_GPU_PAINT_TELL_OK` only while a failure is kept) or the person chooses another way. Each kept problem offers "Paint on the processor" (`--use-paint TARGET cpu`, the person's explicit choice) and Open Graphics settings, in the notification and on the page.
- GPU power: power-profiles-daemon's GPU actions (amdgpu_dpm, amdgpu_panel_power) as switches; they are shown with one GPU as well.
Nothing is written until Apply. Defaults clears the main GPU, the render choices and the copy-back choice; a value equal to the machine's record is not written, so a better record later reaches everyone who never chose.

Commands
-------------
sparky-stereo-gpu-env: what the page decides, for programs that start programs (--category, --app ID or the path of a desktop file, --choice, --3d, --profile, --print, --shell, --ask, --session, --list, --json, --problems, --notify). Plasma's launcher (KIO, kf6-kio 6.30.0-1+stereo3d6 and later) asks it with --app for every program whose desktop entry does not set PrefersNonDefaultGPU; libmedia-gpu-route asks it which GPU players decode on. Exit status 4: the person's choice cannot be used; 5: Automatic cannot place the program now (below).
sparky-stereo-gpu-run [--category C | --app ID | --choice GPU] [--3d] COMMAND: starts a program on its GPU; in Steam, set a game's launch options to `sparky-stereo-gpu-run --category games %command%` (add --3d for a program presenting 3D). A GPU already chosen in its environment (DRI_PRIME, MESA_VK_DEVICE_SELECT, VK_LOADER_DRIVERS_SELECT, __NV_PRIME_RENDER_OFFLOAD) is kept. When the chosen GPU cannot be used, the program does not start on another one: with a display it asks on which GPU that can draw the program starts this time (kdialog), otherwise it says why and does not start it (exit status 4). A missing or failing sparky-stereo-gpu-env is said, and the program does not start.
sparky-stereo-gpu-record (root): --apply-known, --set-best GPU [--copy-back true|false] [--model TEXT] [--measurement TEXT], --copy-back true|false|unset, --set-paint ID.desktop VENDOR:DEVICE cpu|batch|unset [--measurement TEXT], --forget, --show; --root DIR for another system's root.

Nothing fails silently
-------------
Daniel, 2026-11-01: "nothing we do should silently fail or have a fall back - either it works or not and the user must know". The person's chosen GPU is kept, or the step stops and says why, and the other GPUs are offered only as the person's explicit choice.
- A GPU chosen by its PCI address, or as Integrated or Discrete, for the desktop or for a kind of program, is checked whatever the number of GPUs: not in the computer, in it with no graphics driver (the kernel lists it on the PCI bus with no DRM device, as an NVIDIA card whose driver did not install), with no render node, or with a render node the account may not open, or no GPU of the chosen kind. Nothing is put in its place. Mesa would not say it either: a DRI_PRIME that names no GPU selects the default GPU, logged only at Mesa's info level (src/loader/loader.c).
- What failed, why and what to do are said in the person's language: on stderr (sparky-stereo-gpu-env, sparky-stereo-gpu-run, the session's log), on the Graphics page (each problem with a "Use NAME" button for every GPU that can draw; Apply saves the choice) and in a notification at login and whenever a problem is kept: the edition's one engine, sparky-stereo-problems, keeps each problem and its session notifier shows it (ORDER 350), with the same "Use NAME" actions (`sparky-stereo-gpu-env --use KEY GPU`) and Open Graphics settings. Each saved choice's problem is kept in the person's ~/.local/state/sparky-stereo-problems until the choice works again; `sparky-stereo-gpu-env --problems` lists them, `--notify` starts the session's notifier.
- The desktop: a saved main GPU that cannot draw is said and kept at login; KWin's own order draws that login, because nothing could show the person why without a desktop, and the notification offers the GPUs that can draw.
- Automatic and Follow the power profile are rules, shown on the page with the GPU they give: when the profile asks for a kind of GPU the computer does not have, the GPU that draws the desktop, and the page says so; when the GPU measured best for the computer is not there, the page says that, not "not measured". A power profile that cannot be read (no system bus, power-profiles-daemon not running or not answering, a profile name this page does not know) is said and is never taken for Balanced: browsers on Automatic, and every kind that follows the profile, cannot be placed until it is read. An explicit --profile or SPARKY_STEREO_POWER_PROFILE is honoured; a value that names no profile is a wrong argument. Automatic is a rule, not the person's choice, so its problem has its own exit status, 5 (browsers on Automatic while the profile cannot be read), said and kept as for 4: a kind the person set to Follow the power profile exits 4.
- The machine record that cannot be written fails the package's configuration and its removal (Debian Policy 6.1 and 6.7), said by sparky-stereo-gpu-record and kept by the engine in /var/lib/sparky-stereo-problems; at boot the service fails and keeps it the same way. systemd's reload after installation is said and kept, and the package configures, as debhelper's own reload does.
- Plasma's launcher (kf6-kio 6.30.0-1+stereo3d8, ORDER 346g) starts no program on a GPU the person did not choose: when sparky-stereo-gpu-env exits 4, the launch from the menu, KRunner or Dolphin fails with the program's name and the command's own words (KIO's launch-failure path, a notification in Plasma), and the kept problem's notification offers "Use NAME" for each GPU that can draw. A command that fails, crashes, cannot be started or does not answer within five seconds is said the same way. Where the person chose nothing and Automatic cannot place the program now (exit status 5), the program starts as the session would, and the problem is kept and notified. sparky-stereo-gpu-run, asked to start a program on its GPU, asks or does not start it on 4 and on 5 alike.

Dying at start (ORDER 467)
-------------
Daniel, 2026-11-08, "I could not launch waterfox", "attempted twice": a browser sent to the RTX died in its first seconds and the person saw nothing, because the launcher had already finished its job.
The session's systemd runs every program KIO starts as a transient service, `app-NAME@ID.service` (KIO's `SystemdProcessRunner`; XDG standardization for applications, systemd.io/DESKTOP_ENVIRONMENTS), and it knows how each one ended: the three real deaths on the station were `Main process exited, code=dumped, status=11/SEGV` and `Failed with result 'core-dump'` in the user journal, told to nobody.
So the watch is systemd's, not a process of ours.
`share/systemd/user/app-.service.d/10-sparky-stereo-graphics.conf` (a drop-in named `app-.service.d` applies to every unit whose name starts with `app-`, systemd.unit(5)) names two handlers: `OnFailure=sparky-stereo-gpu-died@%n.service` and `OnSuccess=sparky-stereo-gpu-survived@%n.service`.
- `sparky-stereo-gpu-env --died UNIT` asks systemd (D-Bus, the unit's own properties) how the program ended and keeps a death in the problems engine, key `died-NAME`, only when all of these hold: it was sent to a GPU by this page (the unit's environment holds the variables the resolver prints for its desktop entry, or KDE's own PrefersNonDefaultGPU key with a GPU variable), it ended by a crash, a non-zero exit status or another failed result within the window, and it was not killed (SIGKILL) or ended by SIGTERM, SIGINT, SIGHUP or SIGPIPE, which systemd counts as clean. It says what failed ("Sparky Browser stopped right after it started on NVIDIA GeForce RTX 3060: it crashed (signal 11)."), keeps the program's last output lines from the journal, and offers "Use NAME" for the GPU its desktop entry can name (the desktop's GPU, PrefersNonDefaultGPU=false; the discrete GPU, true) through `sparky-stereo-gpu-env --use-app ID GPU`, which writes that key in the person's copy of the entry, as the page does, and ends the death. The program is never started again.
- `sparky-stereo-gpu-env --survived UNIT` ends the kept death of a program that ended cleanly after running longer than the window. The handler unit has `ConditionPathExistsGlob=` on the engine's records, so systemd starts no process at all when no death is kept (measured: `ConditionResult=no`, no PID).
- Not told: a program that ended cleanly (a launcher, a single-instance program handing over to the one already running, a person closing it), a program this page sent nowhere, a crash after the window, a unit that is not one of KIO's (`app-NAME@autostart.service` from the XDG autostart generator has no hexadecimal ID, and gets no GPU variables).
- The window is `[Launch] DiedWithin=` in `~/.config/sparky-stereo-graphicsrc`, 10 seconds when it is not there, 0 turns the notice off. It is measured, not designed: the three real deaths took 3.08, 4.41 and 5.94 seconds from the service's start to its failure (the browser's own error came at 1.8 to 3.2 s, then its crash handler ran for the rest), so 10 s covers the worst with margin and keeps a crash of an hour-old window out.
- It misses what systemd does not run for KIO: a program started from a terminal, Steam's launch options (`sparky-stereo-gpu-run` replaces itself with the program, and Steam owns the game), a program started by another toolkit (GLib's launcher uses a scope, which keeps no exit status), and KIO in its forking mode (systemd older than 250). The drop-in is read by a running session's manager at the next `systemctl --user daemon-reload` or login.
- Tests: `autotests/died-test.sh` (ctest, a stand-in systemd on a private bus: 65 checks) and `autotests/died-systemd-test.sh` (a real systemd user manager in a container; programs started the way KIO starts them: 16 checks). Cost of the drop-in for a program that starts and ends normally, measured with 4 alternating rounds of 60 runs: about 1 ms more from the request to the program's first instruction, about 3 ms more for the whole cycle including its end, about 3 ms more CPU in the user manager, and no extra process.
